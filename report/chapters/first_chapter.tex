This chapter covers the implementation of Fiorino.

\section{Architecture}

Fiorino is written in C17 and uses OpenSSL 3.x for cryptography and password
input. The current build and supported command-line environment are GNU/Linux,
while the source code works on any POSIX.1-2008 platform.

\paragraph{The CLI programs}
The project is divided into a shared C library and four command-line programs:

\begin{itemize}
    \item \texttt{fiorino-encrypt} encrypts a regular file into a vault;
    \item \texttt{fiorino-decrypt} decrypts a vault entry into the current directory;
    \item \texttt{fiorino-delete} removes an encrypted entry from a vault;
    \item \texttt{fiorino-list} prints the names of entries in a vault.
\end{itemize}

Each program has its own executable; there is no combined \texttt{fiorino} command dispatcher.

\paragraph{The library}
The library implements...

\begin{itemize}
    \item vault setup and authentication
    \item file encryption to vault
    \item file decryption from vault
    \item file deletion from vault
    \item listing of the files encrypted in a vault
    \item encrypted file bundle serialization
\end{itemize}

The library also features more general-purpose helpers that are considered unstable
but are technically not Fiorino-specific, for purposes such as...

\begin{itemize}
    \item command-line programs parse options, read passwords
    \item install signal handlers
\end{itemize}

The encryption API accepts an already-open \texttt{FILE *} and a separate
output basename.

\section{Vaults and passwords}

Vault data is stored below \texttt{\textasciitilde/.fiorino}. Each vault is a
subdirectory containing an authentication record and encrypted files:

\begin{verbatim}
~/.fiorino/<vault>/.auth
~/.fiorino/<vault>/<basename>.enc
\end{verbatim}

\paragraph{The \texttt{.auth} record}
Each operation that reads or writes to a vault, checks the vault's \texttt{.auth}
record for authentication of the subject through the passphrase.

The authentication record contains a random 32-byte salt
and a 32-byte PBKDF2-HMAC-SHA-256 verifier, computed with 600,000 iterations
as per \href{https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html}
{OWASP's Password Storage guidelines}.

\paragraph{Password input and evaluation}
Passwords are read with OpenSSL's terminal UI and are not echoed or passed as
command-line arguments.

Encryption prompts twice; decryption, deletion, and
listing prompt once, and the user reads a string presenting the action that
is about to be authorized by authenticating.

The entered password is processed with the stored salt, and the result is
compared with \texttt{CRYPTO\_memcmp}. This verifier authenticates access to
the vault; it is separate from the key derived for each encrypted file.

\section{Encryption and bundle format}

For each file, Fiorino generates a fresh 32-byte salt and derives a 256-bit
AES key from the vault password with PBKDF2-HMAC-SHA-256. The key is not
stored, as I deemed the architectural choice of a master password less practical
than that of a primary 

OpenSSL's random generator supplies a 16-byte IV. The EVP interface
performs AES-256-GCM encryption and returns the authentication tag separately.
GCM does not add block padding, so ciphertext length equals plaintext length.

The serialized bundle contains, in order:

\begin{enumerate}
    \item the 16-byte IV;
    \item the 32-byte per-file salt;
    \item the ciphertext;
    \item the 16-byte GCM authentication tag.
\end{enumerate}

\section{File operations}

The encryption library receives a seekable regular-file stream. It obtains a
shared \texttt{flock}, measures the stream with \texttt{fstat}, rewinds it,
and reads it progressively. Encrypted output is written to a temporary file
inside the vault. After the write succeeds, Fiorino flushes and synchronizes
the file, renames it to the final \texttt{.enc} name, and synchronizes the
vault directory.

Decryption opens and reads the encrypted bundle, derives the file key, and
checks the GCM tag before opening the plaintext destination. It then writes
the plaintext into the current directory. A successful decryption replaces
an existing file with the same basename. The existing output file's mode is
preserved.

Deletion checks the encrypted file's hard-link count and unlinks it only when
no other hard links are reported. Listing scans an existing vault and writes
one basename per line to a caller-provided stream. The CLI uses standard
output for the listing and standard error for status messages.

\section{Supporting components (of the security design)}

Sensitive buffers such as keys, plaintext, GCM tags, and the CLI password
buffer are cleansed in cleanup paths with \texttt{OPENSSL\_cleanse}.

\paragraph{Logging}
The logger sends severity-filtered messages through syslog. The CLI enables
informational messages, while the library defaults to warnings.

\paragraph{Signal handling}
The CLI programs also install handlers for selected termination signals;
handlers record the signal, and the main flow reports the interruption and exits
at the earliest safe/clean point.

\paragraph{Build-side security}
The Makefile enables optimization, \texttt{\_FORTIFY\_SOURCE=3}, stack-clash
protection, stack-protector-strong, and position-independent code. CLI
executables are linked as PIE with full RELRO, immediate symbol binding, and a
non-executable stack. AddressSanitizer and UndefinedBehaviorSanitizer are also
enabled by default in the build.
